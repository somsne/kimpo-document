# Kimpo 插件数据读写开发指南

## 1. 为什么需要这套规则

Kimpo 的应用数据会同时被表单、列表、报表、动作、导入导出和多种 Editor 使用。如果每个插件自行建业务表或把私有字段塞进任意 JSON，系统就无法统一处理权限、事务、查询、升级、卸载和数据迁移。

因此当前采用一个简单边界：业务结构仍由宿主持有；插件若只需要在每条记录或每条明细行上附加少量固定参数，可以声明“宿主管理的插件内联列”。插件拥有字段语义，宿主拥有实际存储和治理。

Workflow 正在独立重建，不套用本文的存储模型。

## 2. 数据应该放在哪里

| 需求 | 推荐位置 | 示例 |
| --- | --- | --- |
| 一条记录对应一个固定标量 | 托管内联列 | 风险分、同步状态、外部稳定 ID、打印标记 |
| 每条明细行对应一个固定标量 | 明细托管内联列 | 行级校验状态、外部行 ID、算法评分 |
| 多个 Editor 都应认识、用户可配置 | 宿主公共字段 | 客户名称、金额、业务状态 |
| 插件自身设计与临时状态 | 插件本地存储 | KimpoSheet 设计文档、会话信息、可重建缓存 |
| 多行、一对多、任务或历史 | 暂缓，单独设计 | 同步任务、回调尝试、审计流水、消息记录 |
| 文件正文 | 宿主资产服务 | PDF、图片、附件 |
| 密钥 | 安全存储 | OAuth secret、token、私钥 |

如果数据需要被多个 Editor、普通报表或最终用户直接配置，它应成为宿主公共字段，而不是长期隐藏在插件私有列中。

## 3. 声明托管列

在插件 Manifest 的 `data_storage.managed_columns` 中声明逻辑结构。插件不需要、也不会得到物理表名或列名。

```json
{
  "column_id": "external-sync-state-v1",
  "key": "external_sync_state",
  "scope": "record",
  "type": "varchar",
  "max_length": 32,
  "nullable": true,
  "visibility": "host_readable",
  "queryable": true,
  "sortable": false,
  "schema_version": 1
}
```

`column_id` 是数据的长期身份，发布后不要随意改变。`key` 是代码中使用的业务名称，可以在兼容策略允许时演进。数据归属按 `plugin_id + column_id` 计算，而不是按某个运行实例计算，因此停用、重装和更换配置实例不会丢失所有权。

可见性含义：

- `plugin_private`：只服务于所属插件。
- `host_readable`：允许宿主在明确场景中投影给通用动作、打印或外部同步。
- `public_field`：意味着数据应进入公共字段模型。当前版本尚未开放完整 writer，因此不能用于生产绑定。

## 4. 插件如何读取和写入

自有列读写通过 Plugin SDK 的 `Host.ManagedColumns()` 完成。调用时只提供逻辑 selector 和稳定业务目标；宿主从调用身份、一次性 grant、应用、数据表、记录和权限中完成校验。

已保存记录使用稳定 `record_id`。编辑中的表单使用 `session_id + data_table_id + row_key`；主表 row key 为宿主管理的稳定键，明细也使用稳定行键，不能使用屏幕上的第几行。

写入时需要：

- 期望业务版本 `version_no`；
- 期望插件扩展版本 `extension_revision`；
- 幂等键；
- 宿主签发的调用授权。

这样公共字段和插件列可以在同一事务中提交，重试不会重复执行，并发修改也不会互相覆盖。

## 5. 通用动作如何消费其他插件的数据

Form、Print、REST 这类通用插件不应该冒充列所有者，也不应该拿到其他插件的私有目录。P1 提供的是“宿主投影”：设计者选择一个 active `host_readable` 列，并给它一个当前动作内使用的别名。

```json
{
  "managed_projection": [{
    "owner_plugin_id": "com.example.risk",
    "column_id": "risk-score-v1",
    "alias": "riskScore"
  }]
}
```

运行时宿主根据当前主记录或当前明细行读取值。如果表单尚未保存，宿主会把数据库基线和 Mirror 中的编辑值合并，再只传递 `{ "riskScore": 98 }`。插件既看不到物理列，也不能改变目标记录。

各插件的使用方式：

- 表单动作：预填映射可使用 `source_managed_alias: "riskScore"`，目标仍是目标表单的公共字段。
- 打印动作：KimpoSheet 的 B 档打印脚本从 `context.record.managed.riskScore` 读取。手动打印没有动作投影时该对象为空。
- REST 同步：目标形态是宿主按行提供 alias map，插件把 alias 映射到外部 API 字段。当前版本已交付映射器和失败关闭测试，但宿主 Data 批量调度尚未接线，因此还不能作为端到端运行能力使用。外部字段映射不会反向变成宿主字段权限。

投影不存在、列不是 `host_readable`、owner 不匹配、scope 不匹配或行身份不完整时，动作会失败，而不是返回一个猜测值。

## 6. 新增、修改、提取、删除和明细排序

- 新增：公共字段和托管列一起写入；任一步失败整条记录回滚。
- 修改：同时比较业务版本与扩展版本，防止公共字段修改和插件修改相互覆盖。
- 提取/复制：默认不复制私有列。是否复制必须由宿主根据明确业务语义和权限决定。
- 软删除与恢复：值仍留在同一物理记录上，不另建孤立数据。
- 永久删除：跟随宿主记录清理策略执行，插件不能直接删除物理列。
- 明细排序：按稳定明细行身份调整顺序，插件值跟随该行；不能按显示行号搬数据。
- 新建/删除数据表：管理员重新执行 binding 或 retire；插件安装阶段不会猜测目标表并自动 DDL。

## 7. 插件更新与卸载

安装插件只登记声明。管理员将声明绑定到具体应用和数据表后，宿主才会执行容量预检、受控建列、索引和结构回读。

升级时，宿主按稳定 `column_id` 比较新旧声明：

- 新增 nullable 列通常可直接处理；
- 改类型、缩短长度、改变 scope、删除有数据的列都属于不兼容变更；
- 当前没有完整 shadow migration worker 的变更会被拒绝，旧版本与旧数据继续可用；
- 回滚也先做兼容检查，不会先停插件再发现数据不兼容。

停用和普通卸载默认保留列与数据。卸载只把 binding 标记为 retired，重新安装相同插件可以接管。物理 purge 需要审批、引用扫描、备份、审计和专门 worker；当前版本不应直接执行 DROP COLUMN。

## 8. 性能理解

没有托管列的记录继续走快速路径，不增加额外事务和 SQL。存在托管列时，宿主按一次记录操作批量处理，不逐字段或逐记录调用 Sidecar。

内联列适合少量、固定、常查询的标量。如果一个插件需要几十个稀疏字段、大 JSON、频繁心跳或无限增长历史，继续增加内联列会损害表宽、索引和 DDL 运维，这时应停止扩展并设计独立宿主服务。

## 9. 开发检查清单

- Manifest 是否只声明逻辑身份，没有物理名？
- 数据是否真的属于单条记录/明细行上的固定标量？
- 是否错误地把 `permissions.storage` 当作业务数据权限？
- 普通字段目录、列表、导出、打印和 REST 是否默认排除了 `plugin_private`？
- 是否使用稳定 record ID / row key，而不是行号或坐标？
- 写入是否带版本、幂等和宿主 grant？
- 升级失败后旧版本能否继续读取原数据？
- 卸载是否默认保留数据，且没有直接 DROP？
- Go 插件是否在自身目录用 `GOWORK=off go test ./...` 验证？
